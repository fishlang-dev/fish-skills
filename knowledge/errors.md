# Error and warning codes

Generated by scripts/sync.fsh from fishc v0.1.1: each code with what `fishc explain <code>` prints.
A code's first two digits give its area: 00 syntax, 01 types, 02 ownership, 03 async and threads,
04 names, 05 calls and members, 06 control flow, 07 classes, interfaces and enums, 08 forms not
supported, 09 modules and manifests, 10 interop, 11 comptime, macros and tests.

## E0001: syntax error

The parser expected one thing and found another: a missing bracket, comma or operand, or a keyword in the wrong place. The message says what it expected and what it found.

TypeScript reports a syntax error here too. Fish parses all of TypeScript's syntax, plus 'match', '|>' and 'comptime', so code that parses as TypeScript parses here too.

To fix it, look at the caret and just before it for what is missing or extra.

For example, this fails:

    function main() {
      console.log(1 +);
    }

and this compiles:

    function main() {
      console.log(1 + 2);
    }

## E0101: mismatched types

A value's type doesn't fit where it is used: a string where a number is wanted, an object missing a field its type requires, a function whose parameters differ.

TypeScript reports the same mismatch as 'Type X is not assignable to type Y'. Fish has no 'any' to get around it, and its numbers have sized types, so an 'f64' doesn't fit an 'i64' either.

To fix it, give a value of the declared type, convert it, as in 'String(n)' or 'x as i64', or change the declaration.

For example, this fails:

    function main() {
      const n: i64 = "five";
      console.log(n);
    }

and this compiles:

    function main() {
      const n: i64 = 5;
      console.log(n);
    }

## E0102: a condition that isn't a boolean

An 'if', a loop, '!', '&&' and '||' take a boolean. Fish has no truthiness: 0, "" and null aren't false, and a number or a string is never a condition.

In TypeScript, any value is truthy or falsy, so 'if (count)' means 'count !== 0' and 'if (name)' means the string isn't empty.

To fix it, write the comparison you mean: 'count !== 0', 's.length > 0', 'x !== null'.

For example, this fails:

    function main() {
      const count = 3;
      if (count) console.log("some");
    }

and this compiles:

    function main() {
      const count = 3;
      if (count !== 0) console.log("some");
    }

## E0104: a type that has to be written, since Fish can't work it out

Fish works a value's type out from what it is given, but some declarations give it nothing to work from: an empty array, a 'let' with no value, a function that calls itself, a generic call whose arguments don't say its type argument.

TypeScript would infer 'any' or 'never[]' for some of these. Fish needs a concrete type for every value, since it lays each one out in memory.

To fix it, write the type, as in 'const xs: string[] = []' or 'function f(n: i64): i64', or pass the type argument, as in 'JSON.parse<Point>(text)'.

For example, this fails:

    function main() {
      const xs = [];
      console.log(xs.length);
    }

and this compiles:

    function main() {
      const xs: string[] = [];
      console.log(xs.length);
    }

## E0108: an Option used without checking it, or checked when it is never empty

A value whose type includes 'null', an Option, is used as if it were there: an operator applied to it, or a method called on it. Or the opposite: '!', '?.' or '??' on a value that can never be null.

TypeScript with 'strictNullChecks' reports the first as 'Object is possibly null'; Fish always checks.

To fix it, check the value first with 'if (x !== null)', give a default with '??', or read through it with '?.'.

For example, this fails:

    function main() {
      const m = new Map<string, i64>();
      const n = m.get("a");
      console.log(n + 1);
    }

and this compiles:

    function main() {
      const m = new Map<string, i64>();
      const n = m.get("a");
      console.log((n ?? 0) + 1);
    }

## E0109: a union used without narrowing it to one member

A value whose type is a union is used in a way only some of its members allow, such as assigning a field one member lacks.

TypeScript reports much the same thing. A Fish union is a tagged value that holds one member at a time, and narrowing says which; reading a field one member lacks is 'no such property', E0502, as in TypeScript.

To fix it, narrow the value first with 'typeof', 'instanceof', a comparison of a shared field, or 'match', then use it in that branch.

For example, this fails:

    type Circle = { kind: "circle"; r: i64 };
    type Square = { kind: "square"; side: i64 };
    function grow(s: Mut<Circle | Square>) {
      s.r = 2;
    }
    function main() {
      let c: Circle | Square = { kind: "circle", r: 1 };
      grow(c);
    }

and this compiles:

    type Circle = { kind: "circle"; r: i64 };
    type Square = { kind: "square"; side: i64 };
    function grow(s: Mut<Circle | Square>) {
      if (s.kind === "circle") s.r = 2;
    }
    function main() {
      let c: Circle | Square = { kind: "circle", r: 1 };
      grow(c);
    }

## E0201: use of a moved value

Assigning an array, an object or a string to another variable, or passing it to a function that takes it owned, moves it: the new owner has it, and the old name can't be used any more. Numbers and booleans are copied instead.

In TypeScript, both names would refer to the same object, and a change through one would show through the other. Fish gives each value one owner, which is how it frees memory without a garbage collector.

To fix it, use the value through its new owner, borrow it instead (a parameter typed 'Ref<T>' or 'Mut<T>' borrows its argument), or hand over a copy with '.clone()'.

For example, this fails:

    function main() {
      const a = [1, 2, 3];
      const b = a;
      console.log(a.length, b.length);
    }

and this compiles:

    function main() {
      const a = [1, 2, 3];
      const b = a.clone();
      console.log(a.length, b.length);
    }

## E0202: cannot move out of a borrowed value

A value is moved out of something that only borrows it: a field read out of a 'Ref' parameter, an element out of a borrowed array, a part of 'this' in a method that borrows 'this'. Moving it would leave the owner with a hole.

In TypeScript, reading a field gives another reference to the same object, so this is never an issue there.

To fix it, hand over a copy with '.clone()', borrow the part instead of moving it, or take the whole value owned.

For example, this fails:

    class Bag {
      items: string[] = [];
    }
    function take(b: Ref<Bag>): string[] {
      return b.items;
    }
    function main() {
      const b = new Bag();
      console.log(take(b).length);
    }

and this compiles:

    class Bag {
      items: string[] = [];
    }
    function take(b: Ref<Bag>): string[] {
      return b.items.clone();
    }
    function main() {
      const b = new Bag();
      console.log(take(b).length);
    }

## E0203: conflicting borrows

A value is used while something else borrows it in a way that rules that use out: changed while it is borrowed, or borrowed mutably twice at once, as when the same value is passed as two 'Mut' arguments.

In TypeScript, two references to one object can both change it, and the result depends on the order of the changes. Fish allows many shared borrows or one mutable borrow at a time, which rules out that whole class of bug, and data races with it.

To fix it, end the first borrow before the second use, pass a copy, or restructure so one place makes the change.

For example, this fails:

    type P = { x: i64 };
    function two(a: Mut<P>, b: Mut<P>): i64 {
      return a.x + b.x;
    }
    function main() {
      let p: P = { x: 1 };
      console.log(two(p, p));
    }

and this compiles:

    type P = { x: i64 };
    function two(a: Mut<P>, b: Mut<P>): i64 {
      return a.x + b.x;
    }
    function main() {
      let p: P = { x: 1 };
      let q: P = { x: 2 };
      console.log(two(p, q));
    }

## E0204: a borrowed value doesn't live long enough

A borrow is kept longer than the value it borrows lives: a reference to a block's local kept after the block, or a reference to a temporary kept after its statement.

In TypeScript, an object lives as long as anything refers to it, so this can't happen there. Fish frees a value when its owner's scope ends, so a reference can't outlive it.

To fix it, declare the value in an outer scope so it lives long enough, or keep an owned copy instead of a borrow.

For example, this fails:

    function main() {
      let outer: string[] = [];
      const o: Mut<string[]> = outer;
      let h = { m: o };
      {
        let x: string[] = ["a"];
        const m: Mut<string[]> = x;
        h = { m: m };
      }
      h.m.push("b");
      console.log(h.m.length);
    }

and this compiles:

    function main() {
      let outer: string[] = [];
      let x: string[] = ["a"];
      const o: Mut<string[]> = outer;
      let h = { m: o };
      {
        const m: Mut<string[]> = x;
        h = { m: m };
      }
      h.m.push("b");
      console.log(h.m.length);
    }

## E0205: a variable used before it is assigned

A variable is read before every path that reaches the read has given it a value.

TypeScript reports the same thing as 'Variable is used before being assigned'.

To fix it, give the variable a value where it is declared, or on every branch before the read.

For example, this fails:

    function main() {
      let n: i64;
      console.log(n);
    }

and this compiles:

    function main() {
      let n: i64 = 0;
      console.log(n);
    }

## E0206: cannot change a value through a shared reference

Something is changed through a shared reference, a 'Ref<T>' or a method's 'this' that is read-only. A shared reference only reads what it points at.

In TypeScript, a parameter can change the object it is given. Fish says in a function's signature whether it changes what it borrows, so callers know.

To fix it, take the value as 'Mut<T>' (or declare 'this: Mut<this>' on a method) so it may change it, and pass it a value that can be changed.

For example, this fails:

    class Counter {
      n: i64 = 0;
    }
    function bump(c: Ref<Counter>) {
      c.n += 1;
    }
    function main() {
      let c = new Counter();
      bump(c);
      console.log(c.n);
    }

and this compiles:

    class Counter {
      n: i64 = 0;
    }
    function bump(c: Mut<Counter>) {
      c.n += 1;
    }
    function main() {
      let c = new Counter();
      bump(c);
      console.log(c.n);
    }

## E0207: cannot change a constant

A 'const' is assigned to, or a field of a 'const' is changed. A Fish 'const' is deeply immutable: nothing it holds can change.

In TypeScript, 'const' only stops the name from being reassigned, and the object it holds can still change.

To fix it, declare it with 'let' when it changes.

For example, this fails:

    class Counter {
      n: i64 = 0;
    }
    function main() {
      const c = new Counter();
      c.n = 1;
      console.log(c.n);
    }

and this compiles:

    class Counter {
      n: i64 = 0;
    }
    function main() {
      let c = new Counter();
      c.n = 1;
      console.log(c.n);
    }

## E0301: async-only code outside an async function

'await', 'for await', 'spawn' and the timers run on Fish's async runtime, which runs inside an async function.

TypeScript reports a top-level 'await' outside a module, or one in a plain function, much the same way.

To fix it, make the function 'async', and 'main' too when the program awaits from it.

For example, this fails:

    async function work(): Promise<i64> {
      return 1;
    }
    function main() {
      const n = await work();
      console.log(n);
    }

and this compiles:

    async function work(): Promise<i64> {
      return 1;
    }
    async function main() {
      const n = await work();
      console.log(n);
    }

## E0302: a Promise that is never awaited

An async function's call gives a Promise that does nothing until it is awaited: Fish's promises are lazy, so a call nobody awaits never runs.

In TypeScript, calling an async function starts it at once, and not awaiting it lets it run in the background.

To fix it, 'await' the call, or start it on its own with 'spawn(...)' when it should run alongside.

For example, this fails:

    async function work() {
      console.log("working");
    }
    async function main() {
      work();
    }

and this compiles:

    async function work() {
      console.log("working");
    }
    async function main() {
      await work();
    }

## E0303: a value that can't cross to another thread

A value that can't safely cross to another thread is given to something that may run there: a 'spawn'ed task, a 'shared' value, a 'Channel'. A borrow of a local or a 'Cell' would let two threads reach the same memory without a lock.

TypeScript runs on one thread, so it has no such rule; Fish's runtime runs tasks on every core.

To fix it, give the task owned values (clone what it needs), and use 'Atomic', 'Lock' or 'shared' for state threads share.

For example, this fails:

    async function first(xs: Ref<string[]>): Promise<string> {
      return xs[0];
    }
    async function main() {
      const names = ["a"];
      const name = await spawn(first(names));
      console.log(name);
    }

and this compiles:

    async function first(xs: string[]): Promise<string> {
      return xs[0];
    }
    async function main() {
      const names = ["a"];
      const name = await spawn(first(names.clone()));
      console.log(name, names.length);
    }

## E0601: a path that ends without giving a value

A function says it returns a value, but some path through its body reaches the end without returning one.

TypeScript reports the same thing as 'Function lacks ending return statement and return type does not include undefined' (TS2366); its 'noImplicitReturns' option is stricter still.

To fix it, return a value on every path, often by adding a final 'return' or an 'else'.

For example, this fails:

    function sign(n: i64): i64 {
      if (n > 0) return 1;
      if (n < 0) return -1;
    }
    function main() {
      console.log(sign(2));
    }

and this compiles:

    function sign(n: i64): i64 {
      if (n > 0) return 1;
      if (n < 0) return -1;
      return 0;
    }
    function main() {
      console.log(sign(2));
    }

## E0602: an error thrown where it isn't handled or declared

An error can be thrown somewhere that doesn't handle it or declare it. In Fish, errors are values a function's type states: a function that can throw says 'throws E' after its return type, and its callers catch the error or declare it in turn.

In TypeScript, any function may throw anything, and nothing in its type says so.

To fix it, declare it, as in 'function f(): i64 throws Error', or catch it with try/catch.

For example, this fails:

    function half(n: i64): i64 {
      if (n % 2 !== 0) throw new Error("odd");
      return n / 2;
    }
    function main() {
      console.log(half(4));
    }

and this compiles:

    function half(n: i64): i64 throws Error {
      if (n % 2 !== 0) throw new Error("odd");
      return n / 2;
    }
    function main() {
      try {
        console.log(half(4));
      } catch (e) {
        console.log(e.message);
      }
    }

## E0801: a form Fish doesn't support yet

The code uses a form that parses, since Fish parses all of TypeScript, but that Fish doesn't compile yet. The message names the form, and usually what to write instead.

In TypeScript, the form is valid.

To fix it, rewrite it with what the message suggests. Running 'fishc survey' over a TypeScript project lists the forms it uses that Fish doesn't support yet.

For example, this fails:

    namespace Util {
      export const two = 2;
    }
    function main() {
      console.log(1);
    }

and this compiles:

    const two = 2;
    function main() {
      console.log(two);
    }

## E0802: a TypeScript form Fish leaves out

The code uses a TypeScript form that Fish leaves out on purpose, such as 'var', or changing a string in place.

In TypeScript, the form is valid.

To fix it, write it the way the message says: 'let' or 'const' for 'var', a new string for a changed one. 'fishc lint' finds these forms in TypeScript code and fixes many of them.

For example, this fails:

    function main() {
      var n = 1;
      console.log(n);
    }

and this compiles:

    function main() {
      let n = 1;
      console.log(n);
    }

## W0001: unused binding

A variable or parameter is declared and never used. It is a warning, so the program still builds.

TypeScript reports the same thing with 'noUnusedLocals' and 'noUnusedParameters'.

To fix it, remove it, or name it with a leading '_' when it is unused on purpose.

For example, this warns:

    function main() {
      const unused = 1;
      console.log(2);
    }

and this compiles:

    function main() {
      const _unused = 1;
      console.log(2);
    }
