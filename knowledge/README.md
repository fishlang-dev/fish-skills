# How this pack is written

The pack is what an agent reads before it writes, ports, explains or debugs Fish. Its reader knows
TypeScript and Rust well and knows nothing about Fish, so it will guess from both. Each entry
exists to stop one wrong guess.

## What counts as true

In this order:

1. What `fishc` does with a program. Run it.
2. The compiler's test programs, copied into `examples/`: one file per feature, many
   `// case: <name>` programs in each, every one stating what it prints or how it fails.
3. The compiler's own tables in its source: the error codes, std's source, the survey and lint
   rules, the manifest parser, the usage text.
4. Prose anywhere else, the compiler's README included, which is a lead to check and not a fact.

A claim that can't be shown with one of the first three is left out. A slice that says less and
is right beats one that says more.

## Files

- `VERSION`, `errors.md`, `std-api.md` and `examples/` are generated by `scripts/sync.fsh`. Never
  edit them by hand.
- Every other slice is hand-written and checked by `scripts/verify.fsh`.
- The slices under `compiler/` describe the compiler's source, for people changing `fishc`. They
  follow its main line of development, not the last release.

## Shape of a slice

- `# Title`, then a few lines saying what the slice covers, what it leaves to which other slice,
  and the fishc release it was checked against.
- Numbered sections, `## 1. Topic`, each one thing a reader looks up.
- Inside a section, lead with the rule in one or two sentences, then show it. Where a TypeScript
  or Rust habit leads the wrong way, say which habit and what Fish does instead.
- A pitfall is written as **Symptom**, **Why**, **Fix**. A rule that the compiler enforces is
  shown once accepted and once refused, with the refusal's code.
- Point at the example bank for depth instead of repeating it: "More: `examples/borrow.fsh`".
- A last section, `## Not released yet`, lists what the compiler's source has that the release the
  slice was checked against doesn't. Leave it out when there is nothing to list.
- 300 to 700 lines. Past that, the slice is doing another slice's work.

## Examples are checked

A fenced block opened with `fsh` is a whole program, and `scripts/verify.fsh` runs the compiler on
it. Its comments say what must happen, in the directives the compiler's own tests use.

A block with no directive must check cleanly. One without a `main` is given an empty one, so
declarations stand on their own:

```fsh
type Point = { x: i64; y: i64 };

function sum(p: Ref<Point>): i64 {
  return p.x + p.y;
}
```

`// expect:` gives a line of stdout, in order. The program is built and run:

```fsh
function main() {
  const total = 1 + 2;
  console.log(total); // expect: 3
}
```

`// error:` gives text the compile error must contain. Quote the code, and enough of the message
to pin it down, exactly as the compiler prints it:

```fsh
function main() {
  const a = [1, 2, 3];
  const b = a;
  console.log(a.length, b.length);
}
// error: error[E0201]
```

`// panic:` gives text the panic must print; the program must exit with 101. `// mode: release`
runs the program as a release build, for behaviour that differs there.

A block opened with `fsh fragment` is part of a program and isn't checked. Use one only where a
whole program would bury the point, and keep them under one in ten.

Run the check on a slice before calling it done:

```
fishc run scripts/verify.fsh -- knowledge/<slice>.md
```

## Wording

- Plain sentences. No em dashes, en dashes or ellipsis characters; use a comma, a colon or
  parentheses.
- Compiler messages are quoted exactly, never paraphrased inside quotation marks.
- Say what the code does, not when or why it was built: no plan numbers, roadmap phases, issue or
  finding ids, and no paths on anyone's machine.
- Name a std function only if it is in `std-api.md` or you ran it.
